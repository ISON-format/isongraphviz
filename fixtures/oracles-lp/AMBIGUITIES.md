## Numbers and ranges

**A-01 (2, 4, 5) Whole pixels.** "Every offset and every box dimension is a whole number of pixels." Checked: `3u` is exact because `u` is an integer, `h = 3u+14` / `3u+10` is an integer, every candidate offset is an integer, so each box edge equals a default coordinate plus (or minus) a whole number of pixels and the fractional micro-pixel part of the default position is preserved. The claim holds. The expected `dx`, `dy` are JSON integers. Rows M-*, R*. **Rev 1: PARTLY SUPERSEDED.** The half width is `3.5u` px (width `7u` px, a whole number of pixels). For odd `u` the box edges lie half a pixel from the default coordinate (`X - 3.5u` px), so "the placed position is the default plus a whole number of pixels" still holds (the offsets are whole pixels) but "every box edge is a whole number of pixels from the default" is false for odd `u`; `h = ceil(7u/2)+14|10` rounds the offset up, so a side candidate of an odd-`u` label is flush at 1.5 px from the own node (not 1 px). Rows G-H* (odd u = 3, 1), W (u = 1, 3), every R*; mutants K018 and K019 (half width floored or rounded up) are killed by them. See A-28. **Rev 3:** the half width is `4.5u` px (4,500,000 micro-px per unit); the half-pixel remarks stand with the new parity: the edge of an odd-`u` label lies half a pixel from the default coordinate and `h = ceil(9u/2)+14|10` rounds up by half a pixel (the side candidate of an odd-`u` node label is flush at 1.5 px from its own node). See A-50.

**A-02 (2) `units` has no upper bound.** Only `1 <= units` and "an integer" are stated. Read: any positive integer (a TypeScript `number` is exact up to 2^53, so `3u * 10^6` as a `bigint` is exact for any admissible `u`). Rows H01-H06 use u = 10^6 (a box 6e6 px wide) and 10^5; W rows u = 200. No cap is applied (the three `units cap` mutants are killed by the W rows with u = 40 and 200). Consequence for section 7: see A-16. **Rev 1:** the box of u = 10^6 is 7e6 px wide (half width 3.5e6 px); rows H01-H06 unchanged in shape.

**A-03 (2, 6) Coordinate bound.** "A bigint outside +-2^62 is a TypeError": read as `|v| <= 2^62` valid, so exactly +-2^62 are accepted (rows NF-P62, NF-M62), and nothing beyond is specified (no row). The box edges `X +- 3u px` and `Y +- 13 px` may exceed 2^62 in magnitude: with arbitrary-precision integers (`bigint`) this is harmless; an implementation in 64-bit machine integers would be exact only up to about u = 1.5e12 (2^62 + 3u*10^6 < 2^63); not tested. A float64 implementation is wrong from about 2^53 micro-px (9e9 px), well inside the allowed range: rows NF-*, T06-T08 (mutant "float64" is killed).

**A-04 (6) What "total" means.** Invalid input (`units < 1`, non-integer, out of range) is "a TypeError of the caller's making and is not specified": no rows, `error` column empty everywhere. An unknown `kind` is not mentioned at all: no row. Read: undefined behaviour.

**A-05 (2, JSON) FORMAT.** Coordinates are decimal strings in the corpus files (a decision of this corpus, because micro-pixel values reach 2^62 and a JSON number loses integers beyond 2^53); `units` is a JSON integer; the test adapter must convert the strings to `bigint`. Canonical JSON rule in README.

## Order and identity

**A-06 (3) Order is the array order.** "The result for one label depends only on the labels before it in this order and on `nodes`." The function has no rule that sorts by kind: node labels first is a contract on the caller. Read: process exactly in array order whatever the kinds are. Rows O06 (node, edge) and O07 (edge, node) give different results; random rows R* sometimes interleave kinds (mutants "edge labels first" and "reverse order" are killed).

**A-07 (3, 6) `nodes` order is irrelevant.** The design says "in model node order" but the result is a function of the *set* of node boxes (every box is tested against every candidate). The generator re-runs every core row with shuffled `nodes` and asserts the same output. An implementation may therefore treat `nodes` as a set; the order only matters if some other reading (e.g. pairing the i-th node label with the i-th node) were intended: none is.

**A-08 (2, 6) "Own endpoints included": the function has no notion of an own node.** Section 6 says a candidate must avoid "every drawn node, own endpoints included". There is no identifier linking a label to a node or an edge to its endpoints, so *all* nodes are treated alike; "own endpoints included" holds automatically. Consequences: (a) the claim of the task text that `(0,0)` "is free by construction" is true only with respect to the own node and only when the caller passes the standard default `(cx, cy + 24 px)`: the label box is then flush 1 px below the node box (top = cy+14, node bottom = cy+13; free because the test is strict, A-10). All 11 node candidates are then free of the own node (flush at 1 px or farther: (0,-41) bottom cy-14, (+-h,*) edge at cx+-14), so excluding or including the own node gives the same output for standard defaults. Rows E03, E10, E11, X01. (b) For non-standard defaults the own node does block (rows E15, X02, X04, X05); mutant "ignore the node of the same ordinal" is killed by those rows only. (c) A node label whose node is absent from `nodes` simply has no own obstacle (E14).

**A-09 (2) Duplicates.** Identical nodes, identical labels and labels placed on identical positions are allowed and handled by the rule (E12, I01-I09). A label never collides with itself (it is recorded only after its choice).

## Boxes and the collision rule

**A-10 (4) "Closed integer rectangle" versus the strict inequality.** The boxes are called closed, but the collision test is `a.left < b.right + 1 px` etc., all strict. Read literally: two boxes whose gap is exactly 1 px do **not** collide, a gap of 0 (touching) or negative (overlap) does, a gap of 999,999 micro-px does. Identical boxes collide. Rows G-*, N-*, M-*, NF-*; mutants "non-strict" (K003-K005), "gap 0/2" (K001, K002) are killed.

**A-11 (4) The gap is per axis, not a distance.** The four conditions are an AND of axis tests, so two boxes at a corner collide when both axis gaps are below 1 px (0.8 px / 0.8 px collide, although their Euclidean distance is 1.13 px); a gap of 1 px on one axis separates them whatever the other axis does. Rows G-NC-*, G-LC-*; the Euclidean mutant is killed.

**A-12 (4) Box model.** The label box is centred on `X` (text-anchor `middle`) with the baseline at `Y` (top `Y-10`, bottom `Y+3`); the node box is a 26 px square independent of the real node size. Not checkable by an oracle: if the renderer's `text-anchor` or baseline differs, the model is wrong while the function is right. The 6 px per UTF-16 unit width is a deliberate model (section 8). **Rev 1:** the model is 7 px per unit. `OVERLAP.tsv` also counts collisions under a judge of 8 px per unit (A-30); labels of 24 units (G07, F04) are 168 px wide in the model and 192 px under the judge, which is why some judged collisions remain (A-31). **Rev 3:** the model is 9 px per unit, wider than the 8 px judge of `OVERLAP.tsv`: judged collisions of placed labels can no longer come from the narrower judge (G07: 2 judged label-node pairs under 7 px, 0 under 9). See A-53.

## Candidates and the rule

**A-13 (5) `h` is relative to the default position, not to the node.** The side candidates `(+-h, dy)` are flush against the own node (1 px gap) only when the label is centred on the node (X = cx). With a label offset from the node (rows X03-X05) the side candidates may overlap the own node and are rejected by the rule. No ambiguity in the text, a REMARK.

**A-14 (5) Candidates `(+-h, -6)` of node labels.** Read literally: box `y = cy+8 .. cy+21` (Y = cy+24), x edge at `cx +- 14`: the third slot of the column of side candidates (`-34`: cy-20..cy-7, `-20`: cy-6..cy+7, `-6`: cy+8..cy+21, each 1 px apart). Interplay (REMARK): for `u >= 5` (`3u+1 > 14`) the side candidates overlap the *column* candidates in x, and `(+-h,-34)` overlaps `(0,-41)` in y (cy-27..cy-14) and `(+-h,-6)` overlaps the default `(0,0)` (cy+14..cy+27) in y: if another label is already at the column slot they are blocked. Twelve identical node labels with u = 8 therefore get 1,2,3,4,5,6,11 and then fall back (row I05), while with u = 3 all 11 candidates are used (I04). The edge candidates behave alike for `u >= 4` (`10 < 3u+1`): `(+-h,0)` collide with a label at the default (I07: 1,2,3,6,7 then fallback). **Rev 1: thresholds changed.** With the half width 3.5u the side candidates `(+-h,-34)`, `(+-h,-6)` overlap the column candidates in x when `3.5u + 1 > 14`, i.e. `u >= 4` (node labels; rev 0: u >= 5), and the edge candidates `(+-h,*)` collide with a label at the default when `10 < 3.5u + 1`, i.e. `u >= 3` (rev 0: u >= 4). Twelve identical node labels: u = 1, 2, 3 take candidates 1..11 then fall back (row I04, u = 3); u = 4, 5, 8 give 1..6, 11 and fallbacks (I05, u = 8). Edge labels: u = 1, 2 give 1..11 (I06 has five labels); u = 3, 4, 5 give 1, 2, 3, 6, 7 then fallbacks (I07, u = 4). **Rev 2:** the first-free thresholds stand (node u >= 4, edge u >= 3). With the 18 added candidates, 29 identical node labels of u = 3 take candidates 1..29 and the next ones fall back (F08, 31 labels); 31 identical edge labels of u = 2 likewise (F07); wide edge labels (u >= 3) stack in the eleven column slots 1, 2, 3, 6, 7, 12, 15, 18, 21, 24, 27 (hand-derived, rows I07, I11, H05) because every side candidate shares a y band with a column slot. **Rev 3: SUPERSEDED thresholds.** With half width 4.5u the left edge of a side candidate is `cx + 14` (even u) or `cx + 14.5` (odd u) for node labels and `ax + 10` or `ax + 10.5` for edge labels; a label in the column slot has its right edge at `4.5u`; a side candidate is blocked by it iff `left < 4.5u + 1`. Node labels: u = 2 free (14 < 10 false), u = 3 free by exactly 1 px (14.5 < 14.5 false), u >= 4 blocked; edge labels: u = 2 free by exactly 1 px (10 < 10 false), u >= 3 blocked. So u = 3 (node) and u = 2 (edge) sit exactly on the gap boundary: rows I04 (12 identical node labels u = 3: 1..12), I06, F07 (31 identical edge labels u = 2: 1..29) and, one step wider, I12 (u = 4: 1..6, 11, 12), I05 (u = 8), I07 (edge u = 4: 1, 2, 3, 6, 7, 12).

**A-15 (6) The fallback box.** "If no candidate is free, the chosen offset is `(0,0)`. The placed box is recorded for the labels after it." Read: a fallback label is recorded at the default position like any other, although it collides; later labels must avoid it (rows F09, F10 isolate this: mutants "fallback not recorded", "only defaults recorded", "placed box at the default" are killed by B01, F09, F10, I rows). Also read: the fallback is exactly `(0,0)`, not the least-colliding candidate and not the last one (F07, F08). **Rev 2: SUPERSEDED.** The fallback is no longer `(0,0)`: it is the first candidate (in the order of section 5) with the least cost, the cost being the number of distinct node boxes and placed label boxes that its box collides with (A-36 to A-39). The placed box is still recorded at the chosen position (now a candidate that collides). The rev 1 mutants "fallback is the default", "last candidate" and "candidate 2" are kept and killed by the F rows.

**A-16 (6) "The first candidate": candidate 1 is `(0,0)` and is tried first** (the list begins with `(0,0)` for both kinds): a label with a free default never moves. Read literally; mutant "default not tried" is killed by almost every row.

## Section 7: the grid

**A-17 (7) DEFECT: the grid as literally described misses collisions.** The text: a uniform grid of 64 px cells, indexed by the integer floor of the box edges, stores each box in every cell it touches and tests a candidate "against the boxes of the cells it touches". With the 1 px gap of section 4 this is **not exact** when coordinates are not whole pixels: a stored box whose right edge is at 63.5 px (cell 0) and a candidate whose left edge is at 64.2 px (cell 1) are 0.7 px apart, so they collide by section 4, yet they touch no common cell. The literal grid then returns a position the rule forbids. Whole-pixel inputs do not expose it (an integer gap below 1 px means the boxes touch or overlap, so they share a cell). Rows N-A*x/y-0.5+0.2 and 0.5+0.499999 (12 rows) and the stress row S02 expose it: mutant K269 ("no 1 px growth") is killed by them. **Reading used (and required of the implementation):** the candidate box is grown by 1 px on every side before the cell range is taken (or equivalently every stored box); `tools/lpgrid.py` does this, and the generator asserts that it then equals the all-pairs reference on every row and on 2,000 random inputs. **Rev 1: SUPERSEDED (repaired).** Section 7 of rev 1 now requires the candidate box to be grown by 1 px on each side ("rev 0 omitted it, found by the implementer"), which is the reading this corpus already used. Mutant K269 (no growth) stays as a regression trap: it is killed by 12 N-A rows and S02. The unkillable-mutant reasons below that depend on the growth stand.

**A-18 (7) REMARK: unit of the cell index.** "Cells of 64 px (indexed by the integer floor of the box edges)": the floor is of the edge in micro-pixels divided by 64,000,000 (Python `//`, `Math.floor` of an exact quotient; for `bigint` a floor division, which is *not* the `/` operator of `bigint`, which truncates toward zero). The cell size and the origin of the grid cannot change the output (mutants with 63, 65 and 1000 px cells are unkillable: A-19).

**A-19 (7) REMARK: floor versus truncation cannot be tested through the output.** The design stresses "floor, not truncation toward zero". For an exact-test grid (every candidate is finally tested with the exact rule against the stored boxes found) the cell index function only needs to be monotone: truncation toward zero is monotone, merely putting the cells -63..63 px into one cell, so it costs time and never changes a result. Rows that straddle zero and cell boundaries exist (T01-T10, N-A*, N-B*, N-Z*, NF-*, with edges exactly on multiples of 64 px) and are correct, but no row can kill the "truncation" mutant (K266; verified equal on the 2,000 random inputs as well). A *non-monotone* fault is killed by the negative rows: sign lost (`abs`, K275) and floor on one edge with truncation on the other (K276). The same holds for the "exclusive end" fault (K270, K273): once the 1 px growth of A-17 is applied, the previous cell is always reached. Cell sizes 63, 65 and 1000 px (K271, K272, K274) are output-equivalent. These six (and the dedupe of rev 1, A-34) are listed as unkillable in `MUTANTS.tsv`.

**A-20 (7) DEFECT (claim): "near-linear time" does not hold in general.** The cost of a candidate test is (cells touched) x (boxes per cell). (a) The number of cells a box touches grows with its width, `6u/64 + 1`, and `units` is unbounded (A-02): one label of u = 10^6 touches about 94,000 cells per candidate and per stored copy (rows H01-H06, with at most twelve labels, already dominate the generator time). (b) Boxes concentrate: S03 (1,500 identical labels on one node) puts every box in the same two or three cells, so each candidate test scans a list that grows with the number of labels placed (11 candidates x up to 1,500 boxes) and every label after the 12th is a fallback that adds another box to the same cells: quadratic in the worst case. The default capacities (20,000 nodes, 40,000 labels) over a realistic layout stay near-linear; the guarantee is only "for bounded `units` and bounded density". Not measured here (the corpus has no timings). **Rev 1: PARTLY ACCEPTED.** Section 7 now states that "a layout that puts thousands of distinct nodes a few micro-pixels apart inside one cell is still quadratic; that limit is accepted", and that storing a box again when its exact edges are already stored may be skipped. With the skip, the 1,500 identical fallback boxes of S03 would be stored once, so S03's quadratic cost disappears, but not for distinct boxes. The unbounded cost of wide boxes (`7u/64 + 1` cells per box for any `units`) is not mentioned and stands. Mutant K277 (skip duplicates) is output-equivalent and listed as unkillable. **Rev 2:** the fallback adds a full scan of 29 candidate regions per label that has no free candidate (no early exit); in a crowded cluster (S03: 600 identical labels, 571 fallbacks) every one of those scans meets all the boxes of the cell. See A-42.

## Claims about the picture the design is meant to fix

**A-21 (8) DEFECT (claim): the candidates do not resolve dense layouts, and the fallback re-creates the overlap.** Section 8 says it "separates label boxes from each other and from node discs". That is exact for every label that is not a fallback (the generator asserts that after placement every colliding pair, label-label or label-node, involves a fallback label); but a label for which all 11 candidates collide returns to `(0,0)` on top of whatever blocks it. Numbers (`OVERLAP.tsv`; pairs of colliding boxes, `ll` label-label, `ln` label-node; "before" = every label at its default; the 20-node, 37-edge-label picture on a 20-gon ring with 20 node labels of 3..8 units and edge labels of 2..8 units at the chord midpoints): **Rev 1: SUPERSEDED, numbers re-measured** (new table in A-32). The finding stands: the fallback to `(0,0)` leaves overlap in dense layouts. **Rev 2: SUPERSEDED numbers** (rev 2 table in A-47).

| Layout | before ll / ln | after ll / ln | labels (57) falling back |
|---|---|---|---|
| ring radius 90 px (D01) | 43 / 61 | 30 / 30 | 25 |
| ring radius 140 px (D02) | 15 / 31 | 5 / 6 | 5 |
| ring radius 220 px (D03) | 12 / 6 | 0 / 0 | 0 |
| ring radius 400 px (D04) | 0 / 0 | 0 / 0 | 0 |
| 5x4 grid, 60 px (D05) | 26 / 12 | 22 / 0 | 15 |
| ring radius 120 px, other chords (D06) | 57 / 40 | 21 / 8 | 11 |
| ring radius 90, node labels only (D07) | 7 / 19 | 0 / 0 | 0 |
| ring radius 90, edge labels only (D08, 37 labels) | 15 / 42 | 8 / 12 | 11 |
| 30x30 grid, 58 px, 2,640 labels (S01) | 870 / 622 | 749 / 0 | 749 |

So at ring radius 220 and beyond the picture is resolved (18 collisions to 0); at radius 140 it is mostly resolved (46 to 11, five labels falling back); at radius 90 and on the 60 px grid it is only halved or less, and in the 58 px grid stress the label-label collisions fall from 870 to 749 (the label-node ones vanish, 622 to 0) with 749 of 2,640 labels (28 percent) falling back. In dense layouts the design as written leaves the overlap in place; a smarter fallback (least-colliding candidate, more candidates, a second pass) is outside the text, and the mutants "least-colliding" and "last candidate" show that those variants give different bytes.

**A-22 REMARK: no dominated candidate.** For both kinds and u = 1, 2, 3, 5, 8, 12, 40 the generator builds, by search, node obstacles that make candidate k the first free one for every k = 1..11 (154 constructions, each verified): no candidate is unreachable, so none is dominated by an earlier one in that sense (C rows for u = 1, 4; W rows for the widths). In use the frequencies are very uneven (`CANDSTATS.tsv`, core rows, candidate numbers 1..11, 0 = fallback): edge labels 384 / 80 / 74 / 79 / 80 / 98 / 10 / 22 / 37 / 6 / 9 for candidates 1..11 (148 fallbacks), node labels 271 / 99 / 66 / 18 / 16 / 12 / 3 / 3 / 4 / 3 / 5 (13 fallbacks); the late candidates are used only when the sides are free but the column is not. **Rev 1: re-verified** (154 constructions, all candidates reachable for u = 1, 2, 3, 5, 8, 12, 40, both kinds, with the new widths; no construction needed re-picking: the whole-pixel blocker search handles half-pixel box edges). New frequencies (`CANDSTATS.tsv`, core rows, candidates 1..11, then fallbacks): edge 456 / 115 / 131 / 169 / 100 / 86 / 16 / 33 / 26 / 19 / 46 (513 fallbacks), node 638 / 125 / 127 / 28 / 16 / 13 / 5 / 3 / 4 / 3 / 23 (161 fallbacks); the R2 rows (real layouts) contribute to these counts. **Rev 2: re-verified and extended** (406 constructions: both kinds, u = 1, 2, 3, 5, 8, 12, 40, candidates 1..29 each forced to be the first free one; none is dominated). New frequencies in A-46.

**A-23 (5) REMARK: short edges.** An edge label anchored at the midpoint of an edge shorter than about 26 px lies inside both endpoint boxes at its default (default box `Y-14..Y-1` against node boxes `cy-13..cy+13`), and for edges shorter than a width plus 26 px it collides with at least one endpoint: (0,0) is *not* free by construction for edge labels (rows E08, E16, B05). "Own endpoints included" makes them move; nothing guarantees that a free candidate exists (it often does: E08 and E16 take `(0,-14)`).

**A-24 (5) REMARK: the stack of column candidates.** Column slots are 14 px apart (`-55, -41, 0, 14, 28` for node labels; `-28, -14, 0, 18, 32` for edge labels): for edge labels the step from `0` to `18` is 18 px, not 14, leaving a 4 px free strip (ay .. ay+3) between the default box (ay-14..ay-1) and the `(0,18)` box (ay+4..ay+17): by design the edge's own line (at ay) passes through that strip. No defect, but note that `(0,14)` would have been flush at 1 px.

## Caller concerns and format

**A-25 (2, 3, 8) Hidden elements, the label budget, elision, `text-anchor` and the order contract** are the caller's concern; the function sees only drawn nodes and drawn labels. No row. A caller that passes hidden nodes makes labels avoid invisible things; a caller that passes hidden labels makes visible ones avoid invisible ones: that is a caller bug the function cannot detect.

**A-26 (6) Result type.** `dx`, `dy` must not be `-0` (a `number` computed as `-h` with `h = 0` cannot happen, but `0 * -1` can in a sloppy implementation): `assert.deepStrictEqual` and `Object.is` distinguish `-0` from `0`, while the expected JSON has `0`. Rows with dx = 0 are the majority; an adapter that compares `JSON.stringify` output is blind to the difference (it prints `0`), one that uses `Object.is` is not. Not testable by the corpus bytes; a REMARK for the test harness.

**A-27 (9) Cross-corpus.** The regenerated bytes of `oracles-svg`, `oracles-dl`, `oracles-gl` after the owner decision R-H depend on this function but are not part of this corpus; no claim is made about them.

## Rev 1 (design 37 rev 1, 2026-11-22): changes and new entries

Rev 1: width 7 px per UTF-16 unit, `h = ceil(7u/2) + 14` (node) or `+ 10` (edge), the 1 px growth of the grid query written into section 7, the storage of an identical box may be skipped, and the quadratic cluster limit accepted. Everything generated was rebuilt: all rev 0 row ids and group letters were kept (the constructions of C, W, F and X were re-derived by the same search; the 154 reachability constructions all still work), 12 G-H rows and 19 R2 rows were added, and the random group R has 15 rows (283 rows in all).

**A-28 (4, 5) Half-pixel edges and the 1 px gap, rev 1.** For odd `u` the label box has edges at `X +- (3.5u)` px, i.e. half a pixel; the gap test is exact in micro-pixels, so a node box 1 px (1,000,000 micro-px) from a half-pixel edge does not collide and one 999,999 micro-px away does: rows G-HN*, G-HL* (u = 3, left and right, gaps 1 px, 1 px - 1 micro-px, 0) and G-HC3-* (u = 1). `h` rounds up, so for odd `u` the side candidate is placed 0.5 px farther than flush: the label is 1.5 px from its own node, and for an edge label the left edge of `(h,0)` is 10.5 px (not 10) from the anchor (u = 3: `h = 11 + 10 = 21`, `21 - 10.5 = 10.5`). A REMARK, not a defect: the rounding wastes half a pixel and keeps the offsets whole, as section 2 requires. The mutants "half width floored", "half width rounded up" and "h floored" are killed by these rows and by W (u = 1, 3). **Rev 3:** the odd-`u` half-pixel case now reads: u = 3 gives half width 13.5, `h = 14 + 14 = 28` (node), the side candidate `(h,-34)` has its left edge at `cx + 14.5`, exactly 1 px from the right edge `cx + 13.5` of a label in the column slot `(0,-41)`: free (row I04). Rows G-HN*, G-HL* (u = 3, half-pixel edges at 486.5 and 513.5) and G-HC3-* (u = 1, `h = 5 + 14 = 19`) are re-derived.

**A-29 (R2) FORMAT: inputs from real layouts.** Group R2 takes the `N` (node) and `T` (label) records of `fixtures/oracles-dl/dl/*.dl` as read-only data: `["N", id, role, flags, cx, cy]` and `["T", id, role, x, y, text]` in milli-pixels, multiplied by 1000. Role 0 is a node label, role 1 an edge label; `units` is the length of `text` in UTF-16 units (`len(text.encode("utf-16-le")) // 2`, so characters outside the BMP count twice); the order is the file order, which is node labels then edge labels. The generator asserts that every node label of a file is at `(cx, cy + 24 px)` of the node of the same ordinal (a file already regenerated with placed positions fails this check) and pins the SHA-256 of every source file (`tools/r2.py`): a different source stops the generator.
