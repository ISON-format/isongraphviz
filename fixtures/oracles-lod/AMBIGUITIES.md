## New findings (rev 3 re-derivation)

* **B-01 (Low)** §3 stage 2 says whitespace "in a `type`, `rel` or id" is the JavaScript `\s` class, but an id is `s:` + a verbatim string (IGS/1 §1.2) and the design also says `s:` + anything non-numeric is valid. Reading used: the class applies to `type` and `rel` only; an id containing whitespace (`s:a b`, M22h) stays valid. Other reading: M22h is `INVALID_ID`.
* **B-02 (Low)** §15.2a lists B14 as unit-test-only (identifier length and timing). The corpus keeps B14a-c as ordinary `deriveView` rows (ids of 1,000 and 16,384 UTF-16 units, verdict only, no timing).
* **B-03 (Low)** §15.2 says 155 planned ids and "363 rows at the time of writing"; the corpus now has 386 rows (README is authoritative).
* **B-04 (Low)** The position of the `suggestGroups` `MAX_INPUT_BYTES` check relative to the budget shape check is not stated; I put it immediately after the budget shape (sizes only, before any parse). No vector.
* **B-05 (Low)** Example D prints no bytes or hashes, so nothing in it could be compared byte-wise; every structural fact stated agrees with E07 as generated by this implementation.
* **B-06 (Low)** §3 stage 1 puts `STATE_BYTES` before encoding checks for the standalone verifier; B16vt (exactly 32 MiB of junk) is `SCHEMA`, not `STATE_BYTES` (boundary is inclusive).
* **B-07 (Info)** No remaining disagreement was found between this implementation and the numbers or bytes printed in rev 3 (Examples A-C: scene, layout, states, ids, views, W 3,127 / 3,492 / 3,507).

* **C-02 (Low)** Rev 4 cites B02d as an at-limit row ("a size equal to the limit passes"); my earlier B02d was the over-limit twin. Renamed: B02d / B03d are exactly 20,000 nodes / 100,000 edges (accepted at the default budget); B02e / B03e are one over (`NODE_LIMIT` / `EDGE_LIMIT`).

## Contradictions inside the document

**A-01 (High) §15.2 M08 versus §3 stage 2 and §13: a string for `zoom_milli`.** M08 reads "zoom_milli float, negative, string: `INVALID_NUMBER`". §3 stage 2 (d) and the §13 row "a value of the wrong JSON type ... a string for a boolean or integer" give `SCHEMA` for a string. Reading used: §3/§13 (the authoritative table): float and negative are `INVALID_NUMBER` (M08a, M08b), the string `"500"` is `SCHEMA` (M08c). Other reading: M08c becomes `INVALID_NUMBER`.

**A-02 (High) §7.3 versus E12: "Cap `0` removes every item".** With `keep_forest = true` a spanning forest is never removed, so cap 0 removes every item only when the forest is empty or `keep_forest = false`. Reading used: the field rule; E12 uses `keep_forest:false` (everything elided), E12b uses `keep_forest:true` (forest kept, cap exceeded). Other reading: E12b would elide everything.

**A-03 (High) §5.5 RT2 versus §15.1: "a round-trip vector's expected file is the original state file".** RT2's first form ends with `expandGroup`, whose canonical result in §15.1 is `{"removed":Group,"state":State}`, not a bare state. Only the second form (expand, then collapse) ends in a plain state. Reading used: C15a (collapse then expand) expects the wrapper (its `state` equals the original and `removed` equals the collapsed group; both asserted by the generator); C15b and C15c (expand then collapse) expect the original state bytes. Other reading: the harness unwraps `state`.

**A-04 (High) §15.2 C11b versus §3 stage 4: "the same family listed in two input orders ... `DUPLICATE_GROUP` in both".** `verifyLODState` requires `collapsed` sorted, and stage 4 (`NON_CANONICAL`) precedes stage 5(b); an unsorted state file is therefore `NON_CANONICAL`, never `DUPLICATE_GROUP`. The input-order claim can only be exercised through a builder. Reading used: `replaceGroups` canonically sorts members and the group list before verifying (C11b, C11b2 call `replaceGroups` with two list orders; both give `DUPLICATE_GROUP`), and C11c is the canonical-order state file. Other reading: if `replaceGroups` does not sort, one of the two orders gives `NON_CANONICAL`. (§5.5 says builders "re-sort" only for `collapseGroup`/`expandGroup`; `replaceGroups` and `setPinned` are silent; `setPinned` is said to sort.)

**A-05 (Medium) §12 `deriveAggregateId(sceneSha256, members)` versus §15.1 "`deriveAggregateId` (scene)".** The API takes the hash; the corpus format passes scene bytes. Reading used: the harness derives `scene_sha256` from the scene file (A01-A04, A12). A consequence: the function cannot check that members exist in the scene, so none of my vectors tests a member that is not in the scene (other reading: `UNRESOLVED_NODE/MEMBER`). `expandGroup` with an `{agg}` target likewise needs no scene (the state carries `scene_sha256` and the members); §15.1 says the scene column is needed "when an `{agg}` target needs ids". I fill the scene column for those rows but the expected bytes do not depend on it.

**A-06 (Medium) §13 "empty optional serialized" is `NON_CANONICAL`, but LODState has no optional that is empty-and-omitted.** `label: ""` is valid and canonical (§3, N-7). Reading used: nothing in a state is an "empty optional"; no vector. Other reading: some intended rule (an empty `x-` object? an empty `pinned`?) is missing from §3.

## Gaps in §15.1 (call and result formats)

**A-07 (High) `projectToView` / `resolveFromView` have no way to feed a malformed `View` (S10).** §15.1 derives the view from (scene, layout, state). Reading used (an extension, flagged): an optional `args.view` in the call file replaces the derived view; S10a-S10h use it. Other reading: S10 is an inline test only.

**A-08 (Medium) Location of the budget in the call file.** §15.1: "`options` only for a budget" without the shape. Reading used: `{"api":"deriveView","args":{},"options":{"budget":{"maxWork":N,...}}}` (mirroring `options?: { budget?: Partial<LodBudget> }`); same for `suggestGroups` and `resolveAggregateEdge`. For `deriveView` without a budget the call file is omitted (`input` = `-`).

**A-09 (Medium) `suggestGroups` arguments.** Reading used: `args` = `{"rules":[RuleSpec,...]}`.

**A-10 (Medium) Call files are "canonical IGS-CJ/1" but a malformed budget or a view needs negative or fractional numbers.** Negative integers (view coordinates in S10 call files) cannot be written in IGS-CJ/1; the generator writes call files with the signed IGL-CJ/1 writer. Negative, fractional and above-2^53 budget values (B10) cannot be spelled at all, so B10 covers only an unknown key, `0`, a string and a boolean. Other reading: an `x-`-style escape for such values, or inline tests.

**A-11 (Low) No format for `emptyState`, `hashLODState`, `serializeLODState`, `serializeView`, `checkViewConservation` (stated inline), `resolveInScene`.** No file vectors; A08 (`resolveInScene` of an aggregate is `UNRESOLVED_ADDRESS`) is an IGS API and is not produced.

**A-12 (Low) `.sha256` files.** "Has a `<name>.sha256` beside it": written as the lowercase hex digest plus one line feed (as `oracles-igl`). Expected files that carry a propagated error use the prefixes `IGS:` and `LAYOUT:` exactly as §15.1 says (e.g. `LAYOUT:SCENE_MISMATCH/` for M15, whereas the IGL corpus writes `SCENE_MISMATCH/` without a prefix).

## Gaps in the rules

**A-13 (High) §4 `children`: direct children or all nested descendants?** "ids name nested active groups that are not emitted in `aggregates[]`". Reading used: the direct children of the aggregate's group (`parent == g`), sorted by id ascending. Only a three-level nest distinguishes the readings (N03: one child versus two). Other reading: all strict descendants.

**A-14 (Medium) §3 stage 2 traversal: check each value then recurse immediately, or check all values of an object before recursing?** The text ("depth-first traversal"; "(d) each present value ... then recurse") supports the first; a literal reading of (d) allows the second. They differ only when a scalar defect sits at a key after (in ascending order) a container with a nested defect, for example `zoom_milli:-1` together with a bad member. Reading used: immediate recursion (depth-first). No stored vector contains such a pair, so the corpus is independent of this choice.

**A-15 (Medium) §3 stage 5(a): per-group or per-check?** "per group in `collapsed` order: EMPTY_GROUP, GROUP_TOO_SMALL, DUPLICATE_MEMBER". Reading used: all three checks for group 1, then group 2. Other reading: EMPTY for all groups, then TOO_SMALL for all, then DUPLICATE_MEMBER. Not exercised by a vector with two different defects.

**A-16 (Medium) Identifier and id validity.** "no whitespace": Unicode or ASCII? Reading used: any character with `str.isspace()` (Unicode). `s:` with an empty remainder is accepted as a valid id (IGS/1 §1.2 does not forbid it; FORCE refuses it separately). A lone-surrogate check is applied to every string before shape checks (e.g. a lone surrogate in a hash is `INVALID_STRING`, not `INVALID_HASH`); the text lists it before hash shape. No boundary vectors.

**A-17 (Medium) `x-` value depth.** "at most 64 levels ... counted from that value": reading used: the value itself is level 1, so 64 nested arrays pass and 65 are `TOO_DEEP` (matches M07 and the IGL V20/V21 convention). Keys inside an `x-` object are checked for lone surrogates; duplicate keys inside it only make the file non-canonical.

**A-18 (Medium) Order of checks in `suggestGroups`.** §11 says "after `verifyScene`, `NODE_LIMIT`, `EDGE_LIMIT`" for the work term but does not order rule validation against scene verification or `RULE_LIMIT`. Reading used: budget, then rule-count (`RULE_LIMIT`), then each rule in order (`UNSUPPORTED_RULE` before `INVALID_RULE_PARAM` per spec), then `verifyScene`, limits, work. A spec with a missing or non-string `rule` key is `INVALID_RULE_PARAM` (not stated). An empty rule list gives an empty catalog (not stated). All T-vectors use valid scenes, so the corpus does not depend on this order.

**A-19 (Medium) Where does standalone `verifyLODState` stand on `MAX_STATE_BYTES` / `MAX_INPUT_BYTES`?** §11 lists them as `deriveView` steps 2. Reading used: only `deriveView` applies them (B01, B16 are `deriveView` vectors); the state-only vectors B04, B05, M14b are judged by stages 1-6. Other reading: the standalone verifier also refuses a state over 32 MiB.

**A-20 (Medium) Work formula inputs.** (a) `Lkey` is the longest `nodeKey` of any scene node (not only group members). (b) `R`/`Lrel` are over the relation strings of scene edges (`R = 0`, `Lrel = 0` without edges). (c) `Hids` is summed over **all** `G` groups of the state, inner groups included (the only reading consistent with §14: 398 = 163 + 235). (d) `G` in `Hv` is the state's group count, not the emitted count. (e) `Hs` is the length of the supplied state bytes. (f) for `resolveAggregateEdge` the entry count `V` counts every `rel_counts` entry of bundles, internal counts and `elided`, plus hidden/exposed entries, nodes, edges and bundles (the text says "`rel_counts` entries" only). Only the three §14 values (3,127 / 3,492 / 3,507, all reproduced) and the boundary vectors B08a-f, B15c/d test the formula; B15e/f use `maxEdges` and `maxWork = 1`, which are independent of reading (f).

**A-21 (Low) Position of `WORK_LIMIT` for `resolveAggregateEdge`.** Checked after `verifyScene` and the node/edge limits and before the `STATE_MISMATCH` comparison. Not stated; only B15f (`maxWork` 1 on a matching view) is stored.

**A-22 (Low) `components/1` and `pendant-fold/1` skeleton details.** A self-loop is ignored in the skeleton (§6) and so a leaf with a self-loop is still a leaf (T07); a node of degree 0 never folds. Parallel edges of different relations count once. No ambiguity found; listed because the networkx differential (A-25) relies on the same reading.

**A-23 (Low) `C-elided` is not checkable from a `View` alone.** `Σ elided_edges = 2·items − (removed items with coinciding endpoints)`: the number of coinciding items is not recorded in a view, so `checkViewConservation` can only check an upper bound (2·items). The generator checks C-nodes, C-edges and the bound; `deriveView` (which knows the items) is exact by construction. Inline-only.

## Impossibilities and unreachable branches

**A-24 (Medium) Oversize vectors are generated, not stored.** B01 (a 256 MiB buffer; one byte over the 268,435,456-byte limit; `B01t` is exactly at the limit and fails later with `IGS:INVALID_SCENE/SCHEMA` because the buffer is not a scene), B02/B02d (100,001 and 20,001 nodes), B03/B03d (500,001 and 100,001 edges, 57 MB), B04/B04o (20,001 and 20,000 groups), M14b, B05/B05o (500,001 and 500,000 member entries, 15 MB), B16/B16t (a state of 32 MiB + 1 and exactly 32 MiB), B17/B17o. Their parameters, sizes and SHA-256 are in `generated/GENERATED.tsv`; `python tools/make_oracles.py --materialize DIR` writes the files. The expected verdicts were produced by running the generator's own implementation on the full files. `B04s`/`B04t` (20,001 and 20,000 empty groups, 300 KB) are stored.

**A-25 (High) `suggestGroups` can never hit `MEMBER_LIMIT` or `DEPTH_LIMIT`, and a rule union can never be non-laminar, with the two qualified rules.** A node is in at most one pendant group and at most one component, so entries are at most 2n <= 200,000 (< 500,000) and depth at most 2. Two equal-size pendant or component groups cannot partially overlap; a pendant group is a strict subset of its component. So §6 "`INVALID_GROUP/OVERLAPPING_GROUPS` for a rule-union failure" and the `MEMBER_LIMIT`/`DEPTH_LIMIT` halves of B17 are unreachable; only `GROUP_LIMIT` is (B17: 20,001 hosts with two leaves each, which needs 60,003 nodes and therefore an explicit `maxNodes` of 100,000 because the default budget is 20,000). Also: since a laminar family has at most n - 1 groups, `GROUP_LIMIT` (20,000) cannot be met by any state that binds to a scene inside the default node budget (20,000); it is reachable only in standalone verification or with a raised budget.

**A-26 (Medium) No undirected worked example.** E07 and E17 were hand-checked: in E07 (undirected, `a-x`, `b-x`, `a-b`, group `{a,b}`) the bundle is `(x, Agg)` with `x` the smaller rank, count 2, and `a-b` is internal.

**A-27 (Low) The `Hv` bound.** On all 90 stored `deriveView` vectors the actual view size is at most 12 % of `Hv` (worst case N02: 4,530 of 37,727). No counter-example, no proof. Case analysis suggests relation strings occur at most once per edge in a view (bundle, internal or elided `rel_counts`) plus once in a visible edge address.

**A-28 (Low) The lexical integer rule needs raw number tokens.** Python's `json` hooks `parse_int`/`parse_float` provide them. `00` is not JSON at all (a parse failure, `SCHEMA`), not an `INVALID_NUMBER` (M08k). `1e999` is `INVALID_NUMBER` by token (not by value).

**A-29 (Medium) `scene` validity is only claimed under the oracle's own `verifyScene`.** Hand-built scenes and layouts were accepted by this author's own implementation of IGS/1 §5.8 and IGL/1 §6 (sufficient for the scenes produced); nobody ran the TypeScript verifiers. A scene the real verifier refuses would show up as an `IGS:`/`LAYOUT:` mismatch on the first run of the implementation.

**A-30 (Low) §11: "`WORK_LIMIT` is reachable at the default node and edge budgets" (R = 100,000 relation names of 1,000 bytes).** The arithmetic (168,300,000) is right; I did not build the 210 MB scene (each edge carries its relation twice) and so there is no vector for it; the claim is unverified.
