# ISONGraph Visualize

A reusable, domain-neutral graph visualization pipeline, built in verifiable stages:

```
source (ISON text)  ->  IGS/1 scene  ->  IGL/1 layout  ->  rendering  ->  selection mapped back to the source
      scene-core            scene-core       layout-core        (not started)
```

Every stage is deterministic and byte-exact: the same input always gives the same bytes and the same SHA-256, a layout is bound to the scene it was computed for by a hash derived from verified scene bytes, and every element keeps a typed address back to its place in the source. There is no second ISON parser: sources are read with the published [`ison-ts`](https://www.npmjs.com/package/ison-ts) and [`ison-graph-ts`](https://www.npmjs.com/package/ison-graph-ts) packages.

## What is here

| Path | What it is | Status |
|---|---|---|
| `packages/scene-core` | IGS/1 scene compiler: `compileScene`, `verifyScene`, address resolution in the source and in the scene | done, 283 tests |
| `packages/layout-core` | IGL/1 layout contract: `computeForceLayout`, `computeFixedLayout`, `computeLayout`, `verifyLayout`, `bindLayout`, `verifyReproducible` | done, 282 tests |
| `docs/specs` | the public editions of the frozen specifications: [IGS/1 (scene)](docs/specs/IGS-1.md) and [IGL/1 (layout)](docs/specs/IGL-1.md) | frozen |
| `docs/conformance` | [how to verify the corpora and an independent implementation](docs/conformance/README.md) | |
| `fixtures/oracles` | frozen IGS/1 conformance vectors (32 files, checksums in `SHA256SUMS`) | frozen |
| `fixtures/oracles-igl` | frozen IGL/1 conformance corpus (92 rows in `EXPECT.tsv`, expected bytes generated by independent Python code; see its `README.md`) | frozen |
| `vscode-isongraphviz` | an earlier VS Code prototype that renders `.ison` graphs | prototype, separate from the packages above |

There is no renderer in the packages yet. The packages are not published to npm (`private`, version `0.0.0`); use them from a checkout.

## Try it

Requires Node 22 or newer. Build `scene-core` first, because `layout-core` depends on it by path.

```bash
cd packages/scene-core  && npm ci && npm run build && npm test
cd ../layout-core       && npm ci && npm run build && npm test
```

From `packages/layout-core` (after the build), compile a graph, lay it out, and verify the result:

```js
import { compileScene } from "isongraph-visualize-scene-core";
import { computeForceLayout, bindLayout } from "./dist/index.js";

const source = new TextEncoder().encode(
  "nodes.person\nid name\nalice Alice\nbob Bob\n\nedges.KNOWS\nsource target\n:person:alice :person:bob\n");

const scene = await compileScene(source, "ison-v1");            // IGS/1 scene bytes + SHA-256
const out = await computeForceLayout(scene.sceneBytes,           // IGL/1 layout bytes + SHA-256
  { width: 900, height: 600, margin: 60, iterations: 170, seed: 42 });
await bindLayout(scene.sceneBytes, out.layoutBytes);             // throws unless the layout belongs to this scene
console.log(out.layout.nodes);                                   // x and y are integer thousandths of a layout unit
```

`computeForceLayout` reuses the force layout of `ison-graph-ts` 1.4.1 (pinned by version, lockfile integrity and a digest of every file it ships). `computeFixedLayout` records positions you supply. `verifyLayout` checks an artifact standalone; `verifyReproducible` recomputes a FORCE layout and compares the bytes.

## Known limitations (read before using FORCE on real workloads)

* **FORCE layout is synchronous and its running time is not bounded.** Core's layout cannot be cancelled once started, so run it off your interaction thread. A work budget refuses oversized requests before Core is called (default: 2,000 nodes and 100,000,000 estimated work units, adjustable through `options.budget`), but the budget limits estimated *work*, not *seconds*, and it does not model identifier cost. Node or relation identifiers longer than 1,024 UTF-16 code units are refused for FORCE (`RESOURCE_LIMIT / CORE_KEY_LENGTH`); identifiers up to that length that share a long prefix and differ only at the end can still make a budget-sized workload take tens of seconds (the longest observed was 26.5 seconds, varying by about 2x between sessions on one machine, with no claim that this is a maximum). Do not promise predictable latency for arbitrary or untrusted graphs. Ordinary short identifiers at the budget limit ran in roughly 0.5 to 5 seconds on the test machine.
* Scenes whose identifiers Core cannot represent (for example ids containing whitespace, `:` or `|`, an integer id and a digit-string id that Core would treat as the same node, or more than 50,000 physical edges in one relation, an undirected edge counting twice) are refused for FORCE with `UNSUPPORTED_SCENE`. `computeFixedLayout` is not affected by these limits.
* Verified only on Windows 11 x64 with V8 (Node 22.23.5 and 24.18.0) and Chromium 159. Other hosts, engines and browsers have not been tested. Graphs above 2,000 nodes have not been measured.
* The browser build needs a secure context (`crypto.subtle`); in an insecure context the functions reject with `HashUnavailableError`.

## Specifications and conformance

The contracts are written to be implemented independently:

* [`docs/specs/IGS-1.md`](docs/specs/IGS-1.md): the scene schema, typed addresses, canonical serialization (IGS-CJ/1), hashing, scene verification, source identity, extensions and structured errors.
* [`docs/specs/IGL-1.md`](docs/specs/IGL-1.md): layout identity, the FORCE and FIXED policies, coordinate quantization, canonical serialization (IGL-CJ/1), scene binding, reproducibility, resource controls and structured errors.
* [`docs/conformance/README.md`](docs/conformance/README.md): the frozen oracle corpora (`fixtures/oracles`, `fixtures/oracles-igl`), how each was produced, and how to check them.

The source code cites these documents by section number.
